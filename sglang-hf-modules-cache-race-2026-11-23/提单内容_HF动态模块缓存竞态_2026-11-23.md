# [Bug] 多进程启动下 trust_remote_code 动态模块缓存竞态导致 scheduler 启动失败

> 提单对象：sglang 产品/SRT 开发
> 优先级建议：P1（现网可复现的启动失败，概率性；多机 worker 节点概率最高）
> 提交人：EdwardXuy　日期：2026-11-23

---

## 一、问题概述

使用 `--trust-remote-code` 的模型在多进程方式启动时（单 pod 多卡、`SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`、DP/EP 多 rank，或多机 worker 节点），多个 scheduler 进程会并发首次填充 transformers 的动态模块缓存 `HF_MODULES_CACHE`。transformers 写缓存使用非原子的 `shutil.copyfile`，读者可能 import 到只写了一半的 `tokenization_*.py`，导致：

```
AttributeError: module 'transformers_modules.<repo>.<hash>.tokenization_kimi'
has no attribute 'TikTokenTokenizer'
```

scheduler 进程退出后 TP/EP 通信组断开，其他节点在 `all_reduce` 处报 `gloo Connection closed by peer`，最终 server 启动失败。

**该问题与 CI、多机测试框架无关，是产品启动路径上的缺陷；CI 脚本预热只能作为过渡，无法覆盖现网客户。**

## 三、复现条件

满足以下条件即可概率性复现（与是否 CI 无关）：

1. 模型使用 `--trust-remote-code`（自定义 tokenizer/processor，如 Kimi 系列等）；
2. 单个 pod/节点内启动多个 scheduler 进程（`SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`，或 tp/dp/ep 多 rank）；
3. `HF_MODULES_CACHE` 为**冷缓存**（新容器/pod、缓存被清理、模型源码 hash 目录变化等）；
4. 缓存目录必须是 pod 本地可写目录（当前为 `/tmp/hf_modules`；`/root/.cache/huggingface` 在部分环境只读）。

### 最小复现步骤

```bash
export HF_MODULES_CACHE=/tmp/hf_modules_repro
rm -rf ${HF_MODULES_CACHE}
SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1 \
python -m sglang.launch_server \
  --model-path <本地 trust_remote_code 模型目录> \
  --tokenizer-path <同上> \
  --trust-remote-code \
  --tp-size 16 --device npu ...
# 冷缓存下循环启动 10~20 次，可观察到 AttributeError
```

## 四、根因分析

### 4.1 sglang 侧：每个 scheduler 进程各自加载 tokenizer

`python/sglang/srt/managers/scheduler.py::init_tokenizer()`（最新 main L972；失败版本 L961）中，多模态走 `get_processor()`、文本走 `get_tokenizer()`；**16 个 scheduler 进程没有任何共享或串行化**，冷缓存下会同时执行首次加载。

### 4.2 transformers 侧：缓存读写都不是原子的

缓存目录由 `HF_MODULES_CACHE` 决定（`transformers/utils/hub.py:108`）。本地模型分支（transformers 5.19.0 `dynamic_module_utils.py` L452-L470）：

```python
if not (submodule_path / module_file).exists() or not filecmp.cmp(...):
    shutil.copyfile(resolved_module_file, submodule_path / module_file)  # 非原子：先 truncate 再写
    importlib.invalidate_caches()
```

读取侧（同文件 `get_class_in_module`，L285-L311）：

```python
module = importlib.util.module_from_spec(module_spec)
sys.modules[name] = module
module_spec.loader.exec_module(module)   # 文件被截断时可能"能执行但没有类定义"
...
return getattr(module, class_name)       # L311：抛 AttributeError
```

- `shutil.copyfile` 以 `"wb"` 打开目标文件 → 写入期间其他进程看到的是空文件/半截文件；
- `_HF_REMOTE_CODE_LOCK` 是 `threading.Lock()`（**进程内**），对 16 个独立进程无效；
- 没有校验和/临时文件/原子 rename。

因此：进程 A 正在 truncate+写 `tokenization_kimi.py`，进程 B `exec_module` 读到半截内容 → 模块导入成功但缺少 `TikTokenTokenizer` → `getattr` 抛 `AttributeError`。窗口毫秒级，16 路并发 + 冷缓存时命中概率不低，表现为偶发。

### 4.3 为什么 worker 节点必挂、node-0 侥幸

`python/sglang/srt/entrypoints/engine.py::Engine._launch_subprocesses()`：

- L1285 `_launch_scheduler_processes(...)` 先 fork 所有 scheduler；
- L1398/L1408 才启动 Detokenizer / `TokenizerManager`（在主进程加载 tokenizer）；
- L1298-L1300：

```python
if get_parallel().node_rank >= 1:
    # Non-zero-rank nodes do not run tokenizer processes.
    scheduler_init_result.wait_for_ready()
    ...
    return (...)
```

→ 只有 node-0 的主进程会"顺带"预热本 pod 缓存（而且依赖 scheduler 还在 import 的时序）；`node_rank >= 1` 的 worker 节点缓存始终为空，16 个 scheduler 就是第一批写者。

### 4.4 为什么"缓存到本地"是对的但不能解决问题

`run_npu_testcase.sh` 中的

```sh
export HF_MODULES_CACHE="${HF_MODULES_CACHE:-/tmp/hf_modules}"
```

是为了规避共享盘只读、且**必须保留**。它只消除了跨节点干扰，使每个 pod 的缓存独立且冷启动，竞态因此收敛为 **pod 内 16 进程竞争**，并没有消失。

### 4.5 异常未被捕获

`python/sglang/srt/hf_transformers/processor.py::_get_processor()` 只 `except ValueError`（L387），AttributeError 会直接杀死 scheduler 进程，随后引发全局通信失败。

## 五、影响范围

| 场景 | 是否受影响 |
|---|---|
| `--trust-remote-code` + 单进程 `tp=1` | 基本不受影响 |
| `--trust-remote-code` + 单机多卡/多进程（`SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`、DP/EP） | **受影响，概率性** |
| 多机部署的 worker 节点（`node_rank >= 1`） | **受影响，概率最高**（无 TokenizerManager 预热） |
| 缓存已热的重复启动 | 不受影响 |
| 不使用 `trust_remote_code` 的模型 | 不受影响 |

结论：凡是在冷缓存下用多进程方式启动 `trust_remote_code` 模型的现网客户都可能遇到，属于产品级健壮性问题；问题偶发，容易被误判为环境抖动。

## 六、修复建议

### 主方案 A（推荐）：launcher fork scheduler 之前预热一次

**位置**：`python/sglang/srt/entrypoints/engine.py::Engine._launch_subprocesses()`，在 `_launch_scheduler_processes()`（L1285）之前。该函数在多机场景下**每个节点都会执行**，包括 worker。

**做法**：

1. 把 `Scheduler.init_tokenizer()` 的加载逻辑（多模态 `get_processor` / 文本 `get_tokenizer`）抽成公共函数，例如 `sglang/srt/hf_transformers/loader.py::load_processor_or_tokenizer(server_args, model_config)`，scheduler 与 launcher 复用；
2. 在 launcher 中调用一次，条件：`trust_remote_code=True` 且 `not skip_tokenizer_init`；
3. 捕获所有异常，只打 warning，不阻塞启动。

伪代码：

```python
# engine.py::_launch_subprocesses，在 publish(server_args, ...) 之后
def _warmup_remote_code_cache():
    if not get_model().trust_remote_code or get_serving().skip_tokenizer_init:
        return
    try:
        load_processor_or_tokenizer(server_args, get_model_config())
        logger.info("HF_MODULES_CACHE prewarmed from %s", get_serving().tokenizer_path)
    except Exception:
        logger.warning("HF_MODULES_CACHE prewarm failed", exc_info=True)

_warmup_remote_code_cache()
# 之后再 _launch_scheduler_processes(...)
```

**收益**：预热先于 fork 完成，之后所有 scheduler 只读完整文件，竞态被确定性消除；覆盖 `sglang serve` / `Engine` API / PD 分离等路径，多机非 Ray 场景每节点各自预热。
**成本**：每节点多一次 tokenizer/processor 加载（约 1~3 秒，内存开销相对模型可忽略）。
**风险**：低；预热失败不阻塞启动，行为与现状一致。
**说明**：RayEngine 跨机部署时 driver 预热不覆盖远端 actor，需要方案 B 兜底或在 actor 初始化时预热。

### 加固方案 B（可选）：trust_remote_code 加载加跨进程文件锁

在 `get_tokenizer()`（`hf_transformers/tokenizer.py` L523）/ `get_processor()`（`hf_transformers/processor.py` L236）外层，对 `from_pretrained` 加 `filelock`：

```python
lock_path = os.path.join(os.environ.get("HF_MODULES_CACHE", "/tmp/hf_modules"),
                         ".sglang_hf_modules.lock")
with FileLock(lock_path):
    processor = AutoProcessor.from_pretrained(...)  # 首次填充串行化
```

覆盖所有加载入口，但需注意 NFS 场景文件锁语义；建议作为 A 的加固，不作为唯一方案。

### 上游方案 D（根治，不阻塞本单）：transformers 原子写

`get_cached_module_file` 改为临时文件 + `os.replace`：

```python
tmp_path = submodule_path / f".{Path(module_file).name}.{os.getpid()}.tmp"
shutil.copyfile(resolved_module_file, tmp_path)
os.replace(tmp_path, submodule_path / module_file)
```

可另加跨进程文件锁。需 transformers 发版 → sglang 升级 pin（当前 `transformers==5.19.0`）→ 镜像重建，周期长，建议并行向上游提 issue/PR，不作为现网短期交付路径。

### 不建议：捕获 AttributeError 后重试

会掩盖远程代码真实错误，且 16 个进程同时重试会放大 IO、持续竞争时仍可能失败，不建议作为交付方案。

## 七、验收标准

1. **冷缓存复现验证**：清空 `HF_MODULES_CACHE`，`--trust-remote-code`，单机 `tp=16`（或 `SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`），连续启动 ≥10 次，不再出现 `AttributeError: module 'transformers_modules...' has no attribute ...`。
2. **多机 worker 节点验证**：`node_rank >= 1` 的节点（无 TokenizerManager）单独验证通过。
3. **预热失败降级**：缓存只读/路径异常时仅告警、不阻塞启动，服务按原逻辑运行。
4. **回归**：`--skip-tokenizer-init`、`trust_remote_code=false`、单进程 `tp=1` 行为不变。
5. **启动耗时**：每节点增加 ≤ 5s（记录实测值）。
6. **路径覆盖**：至少 smoke 覆盖 `sglang serve`、`Engine` Python API、PD 分离、RayEngine 各一条用例。
