# 多进程启动下 trust_remote_code 动态模块缓存竞态：根因分析与修复方案

- 日期：2026-11-23
- 关联失败：Nightly Test (NPU) run `43255221761` / job `131471889371`（kimi_k3_w4a8_32p_gpqa）
- 关联代码：sglang `721ef92c4c764bb3c2307378bf13609fc7be7e72`（失败提交），transformers `5.19.0`
- 关联 CI 过渡补丁：PR #52549（仅测试脚本预热，不覆盖现网，本文档说明其定位）
- 结论先行：**推荐在 sglang 产品侧修复（launcher fork 前预热），由开发提单实现；transformers 侧的原子写作为上游根治并行推进，但不作为现网交付路径。**

---

## 1. 结论摘要（TL;DR）

1. 故障不是共享盘、不是多机框架问题，而是 **同一个 pod 内多个 scheduler 进程首次并发填充 transformers 动态模块缓存** 导致的读-写竞态。
2. 直接触发点在 transformers：`get_cached_module_file()` 对本地模型用 **非原子** 的 `shutil.copyfile()` 写缓存，`get_class_in_module()` 可能 import 到只写了一半的 `tokenization_kimi.py`，于是模块能导入但没有 `TikTokenTokenizer`，`getattr` 抛 `AttributeError`。
3. sglang 侧的放大因素是：`SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1` 时每个 pod 起 16 个 scheduler 进程，**每个进程都在 `Scheduler.init_tokenizer()` 里独立加载一遍 tokenizer/processor**，第一次填充缓存时 16 个进程完全并发。
4. node-0 之所以没挂：它的父进程（`TokenizerManager` / Detokenizer）在 scheduler 完成 import、进入 `init_tokenizer` 之前已经把缓存写完整了；worker 节点（`node_rank >= 1`）不创建 tokenizer 进程，缓存始终是冷的，因此最容易中招。
5. 缓存目录必须保持现状：`HF_MODULES_CACHE=/tmp/hf_modules`（pod 本地、可写）。共享盘不可用的前提下，**任何方案都不能依赖"全局/跨节点预热"**。
6. 推荐方案（产品侧，需开发提单）：
   - **主方案 A**：在 `Engine._launch_subprocesses()` 里、fork scheduler 进程之前，按 `Scheduler.init_tokenizer()` 同样的方式预热一次 processor/tokenizer（每节点一次，失败不阻塞启动）。
   - **加固 B（可选）**：在 `get_tokenizer()` / `get_processor()` 的 `trust_remote_code` 加载外加跨进程文件锁。
   - **根治 D（上游）**：给 transformers 提 issue/PR，把 `shutil.copyfile` 改成 temp + `os.replace` 原子替换（可选加文件锁）。
7. 现网影响：任何使用 `--trust-remote-code` + 单机多进程（tp/dp/ep > 1）或单 pod 多卡、且 `HF_MODULES_CACHE` 为冷缓存的部署，都可能概率性启动失败；多机 worker 节点概率最高。

## 3. 根因分析

### 3.1 进程拓扑：每个 pod 16 个 scheduler 进程

用例环境变量（`test_npu_kimi_k3_w4a8_32p_gpqa.py`）：

```python
"SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS": "1",
```

启动参数：`--nnodes 4 --tp-size 64 --enable-dp-attention --attn-dp-size 4`。

每个 pod 16 卡 → 16 个 scheduler 进程（node-0 是 rank 0~15，node-1 是 16~31，以此类推）。每个 scheduler 在 `Scheduler.__init__` 中都会执行 `self.init_tokenizer()`：

```python
# python/sglang/srt/managers/scheduler.py（最新 main: 972 行；失败版本: 961 行）
def init_tokenizer(self):
    ...
    if self.model_config.is_multimodal:
        self.processor = get_processor(...)      # → AutoProcessor.from_pretrained
        self.tokenizer = get_tokenizer_from_processor(self.processor)
    else:
        self.tokenizer = get_tokenizer(...)      # → AutoTokenizer.from_pretrained
```

**没有任何跨进程共享或串行化机制**：16 个进程各自独立加载。

### 3.2 加载链路

```
Scheduler.init_tokenizer
  → sglang/srt/hf_transformers/processor.py::get_processor (L236) / _get_processor (L272)
  → transformers.AutoProcessor.from_pretrained (L379)
  → transformers/models/auto/tokenization_auto.py::from_pretrained
  → transformers.dynamic_module_utils.get_class_from_dynamic_module (L622)
  → get_class_in_module (L311: return getattr(module, class_name))
```

### 3.3 transformers 缓存机制的两个缺陷

缓存目录由 `HF_MODULES_CACHE` 决定（`transformers/utils/hub.py:108`）：

```python
HF_MODULES_CACHE = os.getenv("HF_MODULES_CACHE", os.path.join(constants.HF_HOME, "modules"))
```

本地模型（本用例 `--tokenizer-path` 指向 ModelScope 本地目录，`is_local=True`）走这个分支（transformers 5.19.0 `dynamic_module_utils.py` L452-L470）：

```python
if not (submodule_path / module_file).exists() or not filecmp.cmp(
    resolved_module_file, str(submodule_path / module_file)
):
    (submodule_path / module_file).parent.mkdir(parents=True, exist_ok=True)
    shutil.copyfile(resolved_module_file, submodule_path / module_file)   # ← 非原子
    importlib.invalidate_caches()
for source_file in get_relative_import_files(resolved_module_file):
    ...
    shutil.copyfile(source_file, target_path)                             # ← 非原子
```

**缺陷 1：写不是原子的。** `shutil.copyfile` 内部以 `"wb"` 打开目标文件，先 truncate 再写；文件在写入期间对任何读者都是"短文件/空文件"。

**缺陷 2：读没有校验。** `get_class_in_module` 在同一把进程内锁下直接读文件、计算 hash、`exec_module`，然后 `getattr`：

```python
module_files = [module_file] + sorted(...)
module_hash = hashlib.sha256(b"".join(bytes(f) + f.read_bytes() for f in module_files)).hexdigest()
...
if getattr(module, "__transformers_module_hash__", "") != module_hash:
    module_spec.loader.exec_module(module)
...
return getattr(module, class_name)     # L311：文件被截断时这里抛 AttributeError
```

截断位置如果恰好是空文件或某个完整语句边界（例如刚写完文件头），`exec_module` 不会报语法错误，但类没有定义 → `getattr` 抛 `AttributeError`，报错信息就是"模块没有这个属性"。

> 注意：`_HF_REMOTE_CODE_LOCK` 只是 `threading.Lock()`（进程内），对 16 个独立进程完全无效。

### 3.4 竞态窗口为什么会被打中

- 每个 pod 的 `/tmp/hf_modules` 在 pod 启动时是**空的**（共享盘不可用后改成了 pod 本地缓存）。
- 16 个 scheduler 进程在 04:35:03 几乎同时 fork，各自 import 完成后在 04:35:07 同时到达 `init_tokenizer`。
- 16 个进程都判断"缓存不存在/内容不一致" → 同时 `copyfile` → 每个进程都在 truncate/写同一个文件 → 互相读到半截文件。
- 窗口只有毫秒级，但 16 路并发 + 首次冷缓存，命中概率不低；文件越大、存储越慢，窗口越大。这解释了：
  - 为什么 node-1 只挂 5 个 rank（其余 rank 在别人写完之后才读）；
  - 为什么 node-2/3 同样冷缓存却全过（纯概率）；
  - 为什么问题看起来是"偶发/不稳定"。

### 3.5 为什么 node-0 没事、worker 节点最容易挂

`Engine._launch_subprocesses()`（`python/sglang/srt/entrypoints/engine.py`，最新 main L1192）的顺序是：

1. L1285 `_launch_scheduler_processes(...)`：fork 所有 scheduler（它们要 import 十几秒才到 `init_tokenizer`）；
2. L1398 `_launch_detokenizer_subprocesses(...)`；
3. L1408 `init_tokenizer_manager_func(...)`：在主进程创建 `TokenizerManager`（加载 tokenizer）；
4. L1298-L1300：

```python
if get_parallel().node_rank >= 1:
    # Non-zero-rank nodes do not run tokenizer processes.
    scheduler_init_result.wait_for_ready()
    ...
    return (...)
```

即：**只有 node-0 会创建 TokenizerManager/Detokenizer**，它们顺带把缓存写完整；`node_rank >= 1` 的 worker 节点直接返回，缓存里什么都没有，16 个 scheduler 就是第一批写者。

### 3.6 为什么"缓存到本地"是对的，但不能解决竞态

- `/root/.cache/huggingface` 在 CI 宿主上是只读挂载，`--trust-remote-code` 又必须写动态模块缓存，所以 `run_npu_testcase.sh` 显式指定了可写的 pod 本地目录：

```sh
export HF_MODULES_CACHE="${HF_MODULES_CACHE:-/tmp/hf_modules}"
```

- 这个改动消除了**跨节点**干扰，必须保留，**不能改回共享盘**。
- 但它也意味着：每个 pod 的缓存都是冷的、独立的，**每个 pod 都必须自己完成首次填充**；竞态从"跨节点"收敛成"pod 内 16 进程"，并没有消失。

### 3.7 现网影响面

满足以下任意组合的部署都可能中招，且与 CI 无关：

- 使用 `--trust-remote-code` 的模型（Kimi 系列、部分 DeepSeek/InternVL 等自定义 tokenizer/processor）；
- 单机多卡、按设备起进程（`SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`、DP/EP 多 rank），或多机 worker 节点（没有 TokenizerManager 预热）；
- `HF_MODULES_CACHE` 为冷缓存：新容器/新 pod、缓存被清理、模型版本变化导致本地源码 hash 目录变化、只读共享盘改本地盘等。

对于单进程（`tp=1`）或缓存已热的环境，基本不会触发，所以问题在开发自测中容易被漏掉。

## 4. 方案对比

> 约束：共享盘不可用，`HF_MODULES_CACHE` 保持 pod 本地 `/tmp/hf_modules`；任何方案都不能依赖跨节点/全局预热。

### 方案 A（推荐，产品侧）：launcher fork 前预热一次

**位置**：`python/sglang/srt/entrypoints/engine.py::Engine._launch_subprocesses()`，在 `_launch_scheduler_processes()`（L1285）之前；此时 `server_args` 已解析、model config 已加载，且该函数在**每个节点**都会执行（包括 worker）。

**做法**：
1. 把 `Scheduler.init_tokenizer()` 里"按是否多模态选择 `get_processor` / `get_tokenizer`"的逻辑抽成公共函数（例如 `sglang/srt/hf_transformers/loader.py::load_processor_or_tokenizer(server_args, model_config)`）；
2. 在 launcher 里调用一次，仅当 `trust_remote_code=True` 且 `not skip_tokenizer_init`；
3. 捕获所有异常，只打 warning，**不阻塞启动**；
4. scheduler 侧继续复用同一函数（行为不变）。

伪代码：

```python
# engine.py::_launch_subprocesses，紧挨着 publish(server_args, ...) 之后
def _warmup_remote_code_cache():
    if not get_model().trust_remote_code or get_serving().skip_tokenizer_init:
        return
    try:
        load_processor_or_tokenizer(server_args, get_model_config())  # 与 scheduler 同一加载逻辑
        logger.info("HF_MODULES_CACHE prewarmed from %s", get_serving().tokenizer_path)
    except Exception:
        logger.warning("HF_MODULES_CACHE prewarm failed", exc_info=True)

_warmup_remote_code_cache()
# 然后再 _launch_scheduler_processes(...)
```

**优点**：
- 确定性消除首次填充竞态：预热在 fork 之前完成，16 个 scheduler 只会读完整文件；
- 覆盖 `sglang serve` / `Engine` API / PD 分离等所有经过 `_launch_subprocesses` 的路径；多机（非 Ray）场景每个节点都会各自执行一次；
- 不依赖共享盘、不需要锁、不改 transformers；
- 改动小（约 30~50 行，含抽取公共函数）。

**缺点 / 成本**：
- 每个节点多加载一次 tokenizer/processor：约 1~3 秒、少量内存（相对模型加载可忽略）；
- 多模态模型会顺带构建 image processor，成本略高；如果介意，可只预热 tokenizer 部分（同一份 `tokenization_*.py`），但建议先按完整加载实现，保证覆盖 `processing_*.py` / `image_processing_*.py` 等其他远程模块；
- RayEngine 跨机部署时 driver 的预热不覆盖远端 actor，需要方案 B 兜底或在 actor 初始化时预热。

**风险**：低。预热失败不影响启动，行为与现状一致。

### 方案 B（可选加固，产品侧）：trust_remote_code 加载加跨进程文件锁

**位置**：`sglang/srt/hf_transformers/tokenizer.py::get_tokenizer`（L523）/ `processor.py::get_processor`（L236）外层，或 `Scheduler.init_tokenizer`。

```python
import os
from filelock import FileLock

lock_path = os.path.join(os.environ.get("HF_MODULES_CACHE", "/tmp/hf_modules"), ".sglang_hf_modules.lock")
with FileLock(lock_path):
    processor = AutoProcessor.from_pretrained(...)   # 首次填充串行化，后续命中缓存很快
```

**优点**：覆盖所有加载入口（包括不经过 Engine 的路径）；不增加父进程加载成本。
**缺点**：`filelock` 在 NFS 上的语义不完全可靠（部分客户共享缓存场景）；需要新增显式依赖（当前仅通过 huggingface_hub 间接安装）；所有加载都被串行化（虽然后续很快）。
**建议**：作为 A 的加固项，不作为唯一方案。

### 方案 C（不推荐作为主方案）：捕获 AttributeError 后重试

```python
except AttributeError as e:
    if "transformers_modules" in str(e) and "has no attribute" in str(e):
        # 清缓存/等一会再试
```

**问题**：掩盖远程代码本身的真实 AttributeError；16 个进程同时重试会放大 IO；持续竞争时仍可能失败。属于"把竞态变成概率更低的重试"，不建议作为交付方案。

### 方案 D（根治，上游）：transformers 原子写

修改 `transformers/dynamic_module_utils.py::get_cached_module_file` 的本地分支：

```python
tmp_path = submodule_path / f".{Path(module_file).name}.{os.getpid()}.tmp"
shutil.copyfile(resolved_module_file, tmp_path)
os.replace(tmp_path, submodule_path / module_file)   # 同文件系统原子替换
```

并可选在 `check + copy` 外层加跨进程文件锁。

**优点**：从根上消除"读者看到半截文件"，对所有下游框架生效。
**缺点**：需要 transformers 发版 → sglang 升级 pin → 镜像重建，交付周期长，且不受 sglang/测试侧控制；在客户现场无法单独打补丁。
**建议**：作为根治项向 huggingface/transformers 提 issue/PR，与方案 A 并行，不阻塞现网修复。

### 4.5 对比结论

| 方案 | 层级 | 覆盖现网 | 覆盖全部启动路径 | 改动量 | 风险 | 交付周期 | 建议 |
|---|---|---|---|---|---|---|---|
| **A launcher 预热** | sglang 产品 | ✅ | ✅（Engine/serve/PD；Ray 跨机需 B 兜底） | 小（~30-50 行） | 低 | 一个 PR | **主方案，提单给开发** |
| B 加载加 filelock | sglang 产品 | ✅ | ✅ | 小 | 中低（NFS） | 一个 PR | A 的加固项（可选） |
| C 异常重试 | sglang 产品 | ✅ | ✅ | 很小 | 中（掩盖错误/IO 放大） | 一个 PR | 不建议 |
| D transformers 原子写 | 上游依赖 | ✅（升级后） | ✅ | 小 | 低 | 新版本 + 镜像升级，长 | 并行提上游 |
| 现状（CI 脚本预热） | 测试脚本 | ❌ | ❌ | 已完成 | 无 | 已就绪 | 仅 CI 过渡，产品修复后可移除 |

**结论：产品侧方案 A（必要时叠加 B）是最优可落地路径；transformers 侧 D 是根治但不可作为现网短期交付。现状 CI 预热只能保证 nightly 稳定，不能替代产品修复。**

**为什么方案 A 不是"规避问题"：**

- 它不依赖测试脚本、CI 环境或某个特定镜像，对所有用 `sglang serve` / `Engine` 启动的客户生效；
- 它消除的是故障的**必要条件**——多个进程对同一份冷缓存的并发首次写，而不是靠重试、忽略异常或延长超时；
- 预热发生在进程 fork 之前，结果是确定性的：之后所有 scheduler 都只读完整文件，不存在"概率性能过"；
- 仍需承认：竞态的**缺陷归属在 transformers**（非原子写 + 无校验读），方案 A 是在 sglang 可控范围内让产品不再触发它；方案 D 才是彻底根除。两者不冲突，建议并行。

## 5. 给开发的实施建议（可直接作为工单）

### 5.1 代码位置（最新 main `38ae340`）

| 内容 | 位置 |
|---|---|
| 子进程启动入口（预热插入点） | `python/sglang/srt/entrypoints/engine.py::Engine._launch_subprocesses()`，L1192；在 `_launch_scheduler_processes()`（L1285）之前 |
| worker 节点不建 tokenizer（证明必须每节点预热） | `engine.py` L1298-L1300 |
| node-0 的天然预热（时序侥幸） | `engine.py` L1408 `init_tokenizer_manager_func(...)` |
| scheduler 加载 tokenizer | `python/sglang/srt/managers/scheduler.py::init_tokenizer()` L972（失败版本 L961） |
| 统一加载入口 | `sglang/srt/hf_transformers/processor.py::get_processor()` L236 / `tokenizer.py::get_tokenizer()` L523 |
| 触发竞态的 transformers 代码 | `transformers/dynamic_module_utils.py::get_cached_module_file()`（本地分支 copy）、`get_class_in_module()` L311 `getattr` |
| 缓存目录（保持现状） | `python/sglang/test/ascend/e2e/run_npu_testcase.sh` L21-L24，`HF_MODULES_CACHE=/tmp/hf_modules` |

### 5.2 验收标准

1. 冷缓存复现用例：清空 `HF_MODULES_CACHE`，`--trust-remote-code`，单机 `tp=16`（或 `SGLANG_ONE_VISIBLE_DEVICE_PER_PROCESS=1`），连续启动 ≥10 次，不再出现 `AttributeError: module 'transformers_modules...' has no attribute ...`。
2. 多机场景：`node_rank >= 1` 的 worker 节点（无 TokenizerManager）单独验证通过。
3. 预热失败（例如只读缓存、路径异常）必须是 warning、不阻塞启动，服务仍能按原逻辑启动。
4. `--skip-tokenizer-init`、`trust_remote_code=false`、单进程 `tp=1` 行为不变。
5. 启动耗时回归：每节点增加 ≤ 5s（实测记录）。
6. 至少覆盖 `sglang serve`、`Engine` Python API、PD 分离、RayEngine 各一条 smoke 用例。

### 5.3 边界与注意事项

- 只在 `trust_remote_code=True` 时预热；纯本地非远程代码模型没有动态模块缓存问题。
- 预热必须使用与 scheduler 相同的 `tokenizer_path / tokenizer_mode / tokenizer_backend / revision`，否则 hash 目录不一致，达不到预热效果。
- 不要把缓存改回共享盘；不要依赖"某个进程先跑完"的时序。
- 若选择方案 B，锁文件必须放在可写的 `HF_MODULES_CACHE` 下，并确认 NFS 场景行为；Linux 用 `fcntl.flock`，Windows 不支持（sglang 服务端以 Linux 为主）。
