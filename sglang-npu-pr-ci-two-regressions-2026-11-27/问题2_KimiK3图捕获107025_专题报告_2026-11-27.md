- 汇报对象：主管
- 汇报日期：2026-11-27
- 范围：只分析 Kimi-K3 32P 的 decode 图捕获失败（上游 #51900），不展开问题 1
- 结论时效：截至 2026-11-27

---

## 一、结论摘要

| 项目 | 结论 |
|---|---|
| 现象 | Kimi-K3 32P 服务启动时，Scheduler 在 decode 图捕获阶段退出，`capture_end` 返回 **107025**，CANN 报 `EVENT_WAIT` / `capture model contains a stream that was not joined to the origin stream` |
| 根因 PR | sglang **#51900**（`[Perf] kimi-k3: Order shared-expert side-stream frees on the current stream`，2026-11-21 合入） |
| 失败阶段 | **Scheduler 初始化阶段的 decode NPU graph 捕获**；HTTP server 尚未启动，所以外部表现为 `/health` 3600s 超时 |
| 影响面 | Kimi-K3 32P 三个 nightly 用例（gpqa / prefill / decode-prefix）；GLM、DeepSeek 不受影响 |
| 修复 | sglang **#53214**（open）：NPU 上改用 `record_stream`，避免在 capture 区间内对 alt stream 追加 `wait_stream` |
| CI 覆盖 | 现有 NPU PR 用例和单测**都没有**覆盖“KimiK3MoE SBO + 真实 NPU 图捕获”；PR 流水线在该 PR 上是 0 个 NPU 用例执行 |

**三句话：**

1. 不是“Kimi-K3 的代码没被调用”，而是它在**图捕获的 dummy forward** 里被调用了，而且第一次调用就踩中了 ACL 的跨 stream 捕获规则。
2. 不是“没有 join”，而是 join 完之后又在 alt stream 尾部排了一个 **EVENT_WAIT**，把子 stream 的最后一个任务从 `EVENT_RECORD` 变成了 `EVENT_WAIT`。
3. #53214 把 NPU 分支改回 `record_stream`，不让 `release_shared_output()` 在 capture 区间内执行，alt stream 的尾部保持为 `EVENT_RECORD`，`capture_end` 就能通过。

## 三、服务拉起的阶段划分：为什么说“在 warmup 之前”，但仍在服务拉起过程中

这是本次汇报最需要澄清的一点。

### 3.1 “服务拉起”不是一步，而是六个阶段

| 阶段 | 内容 | 典型日志 |
|---|---|---|
| 1 | 进程启动、权重加载 | `load_weight=...` |
| 2 | KV cache / HiCache 分配 | `kv_cache_allocation=...` |
| 3 | **Scheduler 初始化 + NPU 图捕获** | `Capture target verify NPU graph begin`、`Capturing batches` |
| 4 | HTTP server 启动 | `Uvicorn running`、`Application startup complete` |
| 5 | **startup warmup（服务自己发的预热请求）** | `Using a 448x448 image for ... startup warmup`、`/health` 503 |
| 6 | 服务 ready | `/health` 200 |

问题 2 发生在**阶段 3**；问题 1 发生在**阶段 5**。

### 3.2 为什么说“在 warmup 之前”

- 这里说的“warmup”是 sglang 的 **startup warmup**，特指阶段 5：HTTP server 起来后，服务自己发一个预热请求，把 decode 路径跑一遍。
- 问题 2 的失败发生在阶段 3 的 `capture_decode_graph`，此时 HTTP server 还没启动。
- 11-24 的日志可以直接证明：在 `Scheduler hit an exception` 之前，**没有** `Uvicorn running` / `Application startup complete`；只有 `Capture target verify NPU graph begin` 和 `Capturing batches`。
- 所以准确表述是：**“在 startup warmup 请求之前，但在服务拉起过程之中”**。它不是请求期错误，而是启动期错误。

### 3.3 那 KimiK3MoE.forward 不是在 warmup 里才调用吗？

不是只在 warmup 里调用。`KimiK3MoE.forward` 在阶段 3 和阶段 5 都会被调用：

- **阶段 3（图捕获）**：`DecodeCudaGraphRunner.capture` 会为每个 batch shape 跑一次 `forward_fn`，把计算图录下来。这个 forward 是 dummy forward，但走的是完整的 `KimiK3MoE.forward -> _forward_unfused`。
- **阶段 5（warmup）**：服务自己发预热请求，再次走 decode 路径。
- **阶段 6（正常请求）**：后续请求 replay 已捕获的图。

问题 2 的触发点是**阶段 3 的第一次 forward**，因为这是第一次在 `torch.npu.graph` 的 capture 区间内执行 `release_shared_output()`。等到阶段 5 时，进程已经在阶段 3 退出了，根本走不到 warmup。

用一个时间线表示：

```text
阶段 1  权重加载
阶段 2  KV cache
阶段 3  capture_decode_graph
          -> KimiK3MoE.forward (dummy)
          -> release_shared_output()
          -> alt_stream.wait_stream(current_stream)   <-- EVENT_WAIT
          -> capture_end -> 107025
阶段 4  Uvicorn（未到达）
阶段 5  startup warmup（未到达）
阶段 6  ready（未到达）
```

## 四、错误发生逻辑（逐层）

### 4.1 ACL 的跨 stream capture 规则

ACL 在 capture 时，允许从 origin stream fork 出子 stream，但要求每条子 stream 最终都要汇合回 origin stream，且**子 stream 上的最后一个任务必须是 `EVENT_RECORD`**：

```text
origin stream: ... fork(alt) ... wait(join event) ...
alt stream:    ... compute ... record_event()     <-- 必须是最后一个任务
```

如果子 stream 的最后一个任务是 `EVENT_WAIT`，`capture_end` 会拒绝：

```text
EE9999: The type of the task is not event record nor capture record,
        stream_id=87, task_id=735, task_type=3 (EVENT_WAIT)
error code 107025
```

### 4.2 #51900 改了什么

#51900 的目标是优化显存：在 `_sbo_shared_overlap` 路径下，共享专家在 `alt_stream` 上执行，原来用 `record_stream` 释放输入/输出，导致 prefill 期间缓存分配器保留大量显存。PR 把释放顺序改到 current stream 上，并新增：

```python
def release_shared_output():
    if shared_alt_output is not None:
        self.alt_stream.wait_stream(torch.cuda.current_stream())
        shared_alt_output = None
```

调用点在 `KimiK3MoE.forward` 的非 latent / latent 路径末尾（L1498 / L1540）。

同时，PR 把 `wait_and_finalize_shared_experts()` 里的：

```python
shared_output.record_stream(current_stream)
```

改成了：

```python
if fine_grained_overlap:
    shared_output.record_stream(current_stream)
else:
    shared_alt_output = shared_output
```

也就是说：**非 fine-grained 路径不再对 shared_output 做 `record_stream`，而是把它留到 `release_shared_output()` 里，用 `alt_stream.wait_stream(current_stream)` 来保证生命周期。**

### 4.3 一次 forward 的 stream 任务序列

以非 fine-grained SBO 为例：

```text
current stream:
  ... front / experts ...
  wait_event(shared_event)          # origin 等 alt 的共享专家完成
  expert_output + shared_output     # 消费共享专家输出
  ...

alt stream:
  wait_stream(current)              # issue_shared 开头，alt 等 current
  shared_experts(...)               # 共享专家 MLP
  record_event(shared_event)        # alt 尾部：EVENT_RECORD
  ...
  wait_stream(current)              # release_shared_output：又在 alt 尾部排了 EVENT_WAIT
```

问题就在最后一行：

- `issue_shared()` 已经在 alt 上 `record_event()`，此时 alt 的尾部是合法的 `EVENT_RECORD`；
- `wait_and_finalize_shared_experts()` 已经用 `current.wait_event(shared_event)` 把 alt 汇合回 origin；
- `release_shared_output()` 又调用 `alt_stream.wait_stream(current_stream)`，在 alt 上追加了一个 **EVENT_WAIT**；
- capture 结束时，ACL 看到 alt 的最后一个任务是 `EVENT_WAIT`，判定子 stream 未汇合，返回 107025。

所以不是“没有 join”，而是**join 之后又把子 stream 的尾部改坏了**。

### 4.4 为什么只有 Kimi-K3 受影响

- `release_shared_output()` 只存在于 `KimiK3MoE`；
- 触发条件：`_ep_a2a=True`（DeepEP）、`shared_experts` 非空、`alt_stream` 非空，即 `_sbo_shared_overlap=True`；
- Kimi-K3 32P 用例同时满足 `--moe-a2a-backend deepep`、`--enable-shared-experts-attn-tp`、decode graph；
- GLM 不经过该分支；DeepSeek-V4 走 `dspark.py`，不使用 `KimiK3MoE`。

### 4.5 为什么 CUDA CI 没发现

- 整个 SBO 分支是 NPU-only：`if _is_npu and self._sbo_shared_overlap: issue_shared()`；
- NVIDIA 的 Kimi-K3 测试不会执行这段代码；
- #51900 的 PR 验证是在 GB300 上测显存收益，覆盖不到 ACL 的捕获规则。

## 五、为什么 #53214 的修改能解决

### 5.1 修改内容

```python
-            if fine_grained_overlap:
+            # TODO: Remove this workaround once PTA fixes side-stream graph capture.
+            if _is_npu:
                 shared_output.record_stream(current_stream)
             else:
                 shared_alt_output = shared_output
```

### 5.2 修改后的任务序列

```text
current stream:
  ... front / experts ...
  wait_event(shared_event)
  expert_output + shared_output
  ...

alt stream:
  wait_stream(current)              # issue_shared 开头
  shared_experts(...)
  record_event(shared_event)        # alt 尾部：EVENT_RECORD
  （release_shared_output 在 NPU 上不再执行）
```

关键变化：

- NPU 分支把 `shared_output.record_stream(current_stream)` 恢复了；
- `shared_alt_output` 保持 `None`；
- `release_shared_output()` 里的 `if shared_alt_output is not None` 为假，**不会执行 `alt_stream.wait_stream(current_stream)`**；
- alt stream 的最后一个任务仍然是 `issue_shared()` 里的 `record_event()`，满足 ACL 要求。

### 5.3 为什么 `record_stream` 不会引入新的 capture 任务

`record_stream` 不是 stream 依赖，也不是 `wait` / `record_event` 这类会排入 stream 的任务；它是**缓存分配器的生命周期提示**：

- 告诉分配器：这块显存还被 `current_stream` 使用，不能提前复用；
- 它不会在 alt stream 上追加任何任务，因此不会改变 capture 结束时子 stream 的尾部；
- 它也不会改变数值或执行顺序。

### 5.4 正确性为什么不受影响

- 消费顺序已经由 `current_stream.wait_event(shared_event)` 保证：current 在消费 shared_output 之前，一定等到了 alt 上的共享专家完成；
- `record_stream(current_stream)` 进一步保证：在 current stream 消费完之前，分配器不会把这块 shared_output 回收/复用；
- 这两件事一个管“执行顺序”，一个管“显存生命周期”，互不替代；
- 因此 #53214 既消除了非法的 EVENT_WAIT，又不会让 shared_output 被提前释放。

### 5.5 为什么不是“只在 capture 时跳过 wait”

也可以在 `release_shared_output()` 里加 `if not torch.cuda.is_current_stream_capturing()` 的守卫，效果类似。但 #53214 选择恢复 NPU 的 `record_stream`，原因是：

- 这是 #51900 之前 NPU 的原有行为，风险最小；
- 它同时解决了生命周期问题，而不是只在 capture 时绕过；
- 与 fine-grained 路径的 `record_stream` 行为保持一致；
- 不需要在 forward 里引入 capture 状态判断，逻辑更简单。

```python
graph = torch.npu.NPUGraph()
with torch.npu.graph(graph):
    static_output = static_input * 2
```

它只能证明“单 stream 的 NPUGraph 能 capture”，不能覆盖跨 stream 的 SBO 场景。

### 6.3 为什么单测方案只能覆盖这一种情况

单测的定位是**针对某个具体回归的最小复现**：

- 它直接调用 `KimiK3MoE._forward_unfused()`，用 fake owner 强制走非 fine-grained SBO；
- 它只验证“这条路径在 capture 下是否合法”；
- 它不覆盖模型加载、TP/EP 通信、DeepEP dispatcher、server 启动、warmup、真实请求；
- 因此它很便宜、很稳定，但只能守住这一条路径；下次如果 bug 出在别的层/别的分支，单测不一定能发现。

这就是开发认为“裁层方案更好”的原因：裁层跑的是完整服务拉起链路，覆盖面更广。

## 七、两个验证方案（设计与关键代码块）

### 7.1 方案 A：NPU 单测（最小复现，快速守卫）

**设计**

- 1 张 NPU 卡，不加载 checkpoint；
- 用 `SimpleNamespace` 作为 fake owner，直接调用真实的 `KimiK3MoE._forward_unfused()`；
- 强制 `_sbo_shared_overlap=True`、`_shared_experts_tp_comm=False`、非 `fine_grained_overlap`；
- 用 `torch.npu.NPUGraph` capture 一次 forward，再 replay 比对 eager 输出。

**关键代码块**

```python
owner = SimpleNamespace(
    alt_stream=torch.cuda.Stream(),
    shared_experts=lambda x: x * 2.0,
    _sbo_shared_overlap=True,
    _shared_experts_tp_comm=False,
    use_latent_moe=False,
    _can_overlap_shared_experts_npu=lambda h: False,
    _ep_front=lambda h: None,
    _ep_front_overlap=lambda h: (None, h),
    experts=lambda h, topk: torch.zeros_like(h),
)

graph = torch.npu.NPUGraph()
with torch.npu.graph(graph):
    captured = KimiK3MoE._forward_unfused(owner, hidden, prefix_sum=None)
```

**预期**

- #51900 代码：`capture_end` 报 107025；
- #53214 代码：capture/replay 成功。

**覆盖与局限**

- 覆盖：`KimiK3MoE._forward_unfused` 的 SBO 路径；
- 不覆盖：模型加载、TP/EP、DeepEP、server 启动、warmup、真实请求。

### 7.2 方案 B：单机 12 层裁层 e2e（开发推荐）

#### 裁层到底是什么

核心开关是目标模型 `config.json` 里的：

```json
{
  "text_config": {
    "num_hidden_layers": 12
  }
}
```

如果配置没有 `text_config`（平铺结构），则改顶层 `num_hidden_layers`。

但要强调：**不是“只改一个数字”这么简单**，它依赖代码里已有的两项“truncated config”支持：

1. `KimiK3ForCausalLM.load_weights` 会跳过 `.layers.<id>` 且 `id >= num_hidden_layers` 的权重；
2. `post_load_weights` 会跳过 `full_attention_layer_ids` 中超出实例化层数的 id。

因此做法是：

- 用 `tempfile.mkdtemp()` 建临时目录；
- 把原 checkpoint 的所有文件 **symlink** 过去（不拷贝、不重新生成权重）；
- 只把 `config.json` 的 `text_config.num_hidden_layers` 改成 12；
- 用临时目录作为 `--model-path` 启动 server。

这样只实例化 12 层，目标模型显存显著低于全量，单机 16 卡可以放下；draft 模型仍是原始 `Kimi-K3-DSpark`。

层数选择要注意：Kimi-K3 是 KDA/MLA 混合结构，`is_kda_layer` 用 1-based 的 `kda_layers` 判断；12 层需要至少包含一个 full-attention 层。#53214 作者已经在 12 层配置上验证过；如果某个 checkpoint 的前 12 层全是 KDA，需要把层数调整到包含 full-attention 层。

#### 启动参数（关键项）

```text
--tp-size 16 --attn-dp-size 1
--enable-shared-experts-attn-tp
--moe-a2a-backend deepep --deepep-mode auto
--speculative-algorithm DSPARK --speculative-draft-model-path <Kimi-K3-DSpark>
--cuda-graph-bs-decode 1 4 16
```

环境变量保留 32P 用例的关键项：`SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1`、`SGLANG_RAGGED_VERIFY_MODE=static`、三个 `SGLANG_DSPARK_*`、`STREAMS_PER_DEVICE=32`。

#### 覆盖与局限

- 覆盖：模型加载、TP/EP、DeepEP、共享专家、DSPARK、decode graph capture、warmup、一次真实 decode；
- 不覆盖：4 节点多机通信、全量 61 层、所有层类型组合；
- 资源：单机 16 卡 A3，需要缓存的 Kimi-K3-W4A8 + Kimi-K3-DSpark 权重；
- 适合放在 `extra-b-test-16-npu-a3`，作为 PR 阶段的 16 卡 smoke；如果担心资源，可先放 nightly，稳定后再提升。

### 7.3 两个方案怎么选

| 维度 | 方案 A 单测 | 方案 B 裁层 e2e |
|---|---|---|
| 覆盖范围 | 只覆盖 `_forward_unfused` 的 SBO 路径 | 覆盖完整服务拉起链路 |
| 资源 | 1 卡 | 16 卡单机 |
| 权重依赖 | 无 | 需要缓存 Kimi-K3 权重 |
| 发现新问题的能力 | 弱（只守这一条路径） | 强（能发现加载、TP/EP、capture、warmup 的其他问题） |
| 维护成本 | 低，但依赖内部函数名 | 中，依赖裁层支持 |
| 适合阶段 | PR 快速守卫 | PR smoke / nightly |

**建议：A + B 同时保留。** 方案 B 按开发意见作为主方案，负责“全面覆盖”；方案 A 作为 1 卡快速守卫，负责“便宜、稳定、早失败”。两者不是替代关系。

## 八、结论与建议

1. **问题 2 的根因明确**：#51900 在 NPU-only 的非 fine-grained SBO 路径新增了尾部 `alt_stream.wait_stream(current_stream)`，在 capture 区间内产生 EVENT_WAIT，违反 ACL 规则。
2. **失败阶段明确**：Scheduler 初始化阶段的 decode 图捕获，**在 startup warmup 请求之前，但在服务拉起过程之中**；HTTP server 尚未启动，所以表现为 `/health` 超时。
3. **修复方案明确**：#53214 在 NPU 上恢复 `record_stream`，让 `release_shared_output()` 不再执行尾部 wait；alt 尾部保持 `EVENT_RECORD`，capture 合法；生命周期和数值都不受影响。
4. **CI 覆盖明确**：现有 NPU PR 用例和单测都没有覆盖 `KimiK3MoE` SBO + 真实 NPU 图捕获；PR 流水线在 #51900 上是 0 个 NPU 用例执行。
5. **建议**：
   - 推动 #53214 合入，并用 Kimi-K3 32P nightly 回归；
   - 落地方案 B（12 层单机裁层 smoke）到 `extra-b-test-16-npu-a3`，作为主回归；
   - 保留方案 A（1 卡单测）作为快速守卫；
   - 对 `kimi_k3.py`、`dspark/**`、`hardware_backend/npu/**` 等 NPU 敏感路径，自动触发 NPU CI 或自动加标签，避免再次出现“PR 阶段 0 用例执行”。
