## 一、汇报摘要

近期 nightly NPU 流水线出现两起共性问题。经逐层定位，两起都不是用例问题、也不是镜像/CANN 问题，而是**上游社区 PR 在 NVIDIA 路径验证通过、NPU 路径被破坏**的回归。

| 问题 | 根因上游 PR | 失败阶段 | 影响 | 当前状态 |
|---|---|---|---|---|
| `TypeError: markov_sample_step_triton() got an unexpected keyword argument 'softcap'` | **#51298**（从 #50186 Inkling-2-Small 拆出） | 服务启动完成后的 **startup warmup 首个 decode batch** | DeepSeek-V4、Kimi-K3（所有 DSPARK 模型）服务无法拉起 | sgl-kernel-npu **#1070 已修复**（11-20 合入） |
| Kimi-K3 decode 图捕获 `capture_end` **107025** / `EVENT_WAIT` | **#51900** | Scheduler 初始化阶段的 **decode NPU graph 捕获** | Kimi-K3 32P 三个 nightly 用例连续失败 | sglang **#53214 修复 PR 已提交，尚未合入** |

**关于 NPU PR 流水线拦截情况，结论如下：**

1. 三个上游 PR（#51298、#50186、#51900）的 `PR Test (NPU)` 都是 **0 个 NPU 用例执行**，workflow 却显示 success，属于 false green。
2. 问题 1：PR 套件里**存在**能拦截的用例（`extra-c-acc-test-16-npu-a3` 中的 DeepSeek-V4-Flash W8A8 8p DSPARK 用例），但**没有执行**。
3. 问题 2：PR 套件里**完全没有** Kimi-K3 用例（32P 只在 nightly 多机跑），即使执行也**拦不住**，属于结构性覆盖缺口。

**需要主管支持的事项：**

- 推动社区合入 Kimi-K3 图捕获修复 **#53214**；
- 批准 NPU CI 的三项改进：路径自动触发、DSpark 关键字兼容单测、Kimi-K3 单机 capture smoke 用例；
- 允许在验证阶段手动全量触发一次 `extra-c-acc-test-16-npu-a3`，确认问题 1 可被现有用例拦截。

## 二、问题 1：markov 采样算子不接受 `softcap` 参数

### 2.1 结论

- **根因 PR**：[sglang #51298](https://github.com/sgl-project/sglang/pull/51298)（`[Feat] dspark: Let the draft fold its verify commit and cap step logits`，2026-11-19 07:15Z 合入）。
- **关联 PR**：[sglang #50186](https://github.com/sgl-project/sglang/pull/50186)（`[Feat] inkling2: Support Inkling-2-Small`）。#51298 是从 #50186 拆出的 DSpark 基础改动；#50186 的 merge commit 恰好是 11-19 nightly 的 head，因此首个失败 run 指向它，但**真正引入 `softcap` 关键字的是 #51298**。
- **错误性质**：不是 Triton 编译失败，而是 **Python 关键字不兼容**。sglang 侧新增 `softcap` / `vocab_limit` 参数后，NPU 侧 `sgl_kernel_npu.markov_sample_step_triton` 仍是旧签名。
- **发生阶段**：服务进程启动完成、HTTP server 已监听、**startup warmup 的首个 decode batch**。
- **修复**：[sgl-kernel-npu #1070](https://github.com/sgl-project/sgl-kernel-npu/pull/1070)，2026-11-20 03:50Z 合入。

### 2.2 现场与日志

- 首个失败 nightly：[run 44562390109](https://github.com/sgl-project/sglang/actions/runs/44562390109)（2026-11-19T16:06Z 创建，head `6515ac29d3`）。
- Kimi-K3 gpqa 失败 job：[job 135859074748](https://github.com/sgl-project/sglang/actions/runs/44562390109/job/135859074748)。
- 同夜 3 个 DeepSeek-V4 job 同样失败：
  - [deepseek_v4_flash_0731_w8a8_1p1d_16p_gpqa](https://github.com/sgl-project/sglang/actions/runs/44562390109/job/135763018458)
  - [deepseek_v4_pro_0813_w4a8_1p1d_32p_gpqa](https://github.com/sgl-project/sglang/actions/runs/44562390109/job/135771100368)
  - [deepseek_v4_flash_w8a8_1p1d_16p_prefix90](https://github.com/sgl-project/sglang/actions/runs/44562390109/job/135752813787)

Kimi-K3 job 中 16 个 rank 在 `2026-11-19T20:54:09Z` 同一秒抛出：

```text
File ".../markov_sample.py", line 268, in execute
  return markov_sample_step_triton(**kwargs)
TypeError: markov_sample_step_triton() got an unexpected keyword argument 'softcap'
```

### 2.3 错误发生逻辑

```text
DSpark decode
  -> _draft_step
  -> MarkovSampleStep.execute
  -> sgl_kernel_npu.markov_sample_step_triton(**kwargs)
  -> TypeError: unexpected keyword argument 'softcap'
```

- #51298 在 `MarkovSampleStep` 上新增 `softcap` / `vocab_limit`，并在 `_draft_step` 中**无条件传入**（即使值为 `None`）。
- CUDA 的 `MarkovSampleStep.triton` 已同步支持这两个参数；NPU 的 wrapper 未同步，因此只有 NPU 报错。
- DeepSeek-V4 与 Kimi-K3 都使用 `--speculative-algorithm DSPARK`，共用 `_draft_step`，因此同时中招；GLM 不使用 DSPARK，不受影响。

### 2.4 失败阶段

日志时间线：

| 时间 | 事件 |
|---|---|
| 04:53:38 | `Engine startup timings ... draft_decode=5.84`、`Uvicorn running`、`Application startup complete` |
| 04:53:39 | 进入 Kimi-K3 startup warmup |
| 04:53:40 - 04:54:01 | `/health` 连续 503 |
| 04:54:09 | warmup 首个 decode batch 触发 TypeError |
| 之后 | scheduler 退出，`/health` 等待 3600s 超时 |

结论：不是模型加载，也不是 graph capture；是**服务起来后的 warmup decode**。

### 2.5 修复与残留风险

- sgl-kernel-npu #1070 的处理方式：两个 Markov wrapper 增加 `**kwargs`，**接受并忽略** `softcap` / `vocab_limit`。
- PR 自述验证仅为 `git diff --check`，**没有真实 NPU 运行**。
- 残留风险：NPU 尚未实现 `softcap` / `vocab_limit` 语义。当前 DeepSeek-V4 / Kimi-K3 默认值为 `None`，无影响；未来 Inkling2 MTP 等使用 `step_softcap` 的模型在 NPU 上会**静默忽略**，存在精度偏差风险。

## 三、问题 2：Kimi-K3 decode 图捕获 `capture_end` 107025

### 3.1 结论

- **根因 PR**：[sglang #51900](https://github.com/sgl-project/sglang/pull/51900)（`[Perf] kimi-k3: Order shared-expert side-stream frees on the current stream`，2026-11-21 04:13Z 合入）。
- **错误性质**：Kimi-K3 共享专家 side-stream 路径新增 `alt_stream.wait_stream(current_stream)`，在 decode 图捕获区间内产生 **EVENT_WAIT**，违反 ACL“子 stream 最后一个任务必须是 event record”的规则。
- **发生阶段**：Scheduler 初始化 → `init_all_cuda_graphs` → `capture_decode_graph` → `capture_end`，HTTP server 尚未启动。
- **修复**：[sglang #53214](https://github.com/sgl-project/sglang/pull/53214)，已提交，尚未合入。

### 3.2 现场与日志

- 首个失败 nightly：[run 44922677219](https://github.com/sgl-project/sglang/actions/runs/44922677219)（head `9b4b6b6d`）。
- Kimi-K3 gpqa 失败 job：[job 136978977457](https://github.com/sgl-project/sglang/actions/runs/44922677219/job/136978977457)。
- 复现 nightly：[run 45212673268](https://github.com/sgl-project/sglang/actions/runs/45212673268)，[job 137954231568](https://github.com/sgl-project/sglang/actions/runs/45212673268/job/137954231568)。
- PR 验证 run（CANN 9.2）：[run 45343894905](https://github.com/sgl-project/sglang/actions/runs/45343894905)，[job 138280635172](https://github.com/sgl-project/sglang/actions/runs/45343894905/job/138280635172)。

关键报错：

```text
RuntimeError: capture_end:../torch_npu/csrc/core/npu/NPUGraph.cpp:371
NPU function error: endCaptureErr, error code is 107025
EE9999: ... stream_id=87, task_id=735, task_type=3 (EVENT_WAIT)
Invalid_Argument(EE1017): Capture model validity check failed ...
capture model contains a stream that was not joined to the origin stream
```

### 3.3 错误发生逻辑

- #51900 新增 `release_shared_output()`：

```python
def release_shared_output():
    if shared_alt_output is not None:
        self.alt_stream.wait_stream(torch.cuda.current_stream())
        shared_alt_output = None
```

- 调用点在 `KimiK3MoE.forward` 的非 latent / latent 路径末尾（L1498 / L1540）。
- 触发条件：`_sbo_shared_overlap = _ep_a2a and shared_experts is not None and alt_stream is not None`；Kimi-K3 32P 用例同时满足 DeepEP、共享专家、decode graph。
- ACL capture 期间，子 stream 最后一个任务是 EVENT_WAIT，`capture_end` 校验失败，返回 107025。
- 该 SBO 分支是 **NPU-only**（`if _is_npu and self._sbo_shared_overlap`），因此 NVIDIA CI 完全不执行这段代码，PR 的 GB300 验证覆盖不到。

### 3.4 失败阶段

```text
Scheduler.__init__
  -> init_model_worker
  -> init_all_cuda_graphs
  -> capture_decode_graph
  -> DecodeCudaGraphRunner.capture
  -> capture_one_shape
  -> npu_cudagraph_backend._capture_one
  -> graph_ctx.__exit__
  -> capture_end -> 107025
```

此时 HTTP server 尚未启动，外部表现为 `/health` 长时间不可用、3600s 超时。

### 3.5 修复进展

- #53214 改动（+2/-1）：NPU 上改用 `record_stream`，避免尾部 side-stream wait：

```python
- if fine_grained_overlap:
+ # TODO: Remove this workaround once PTA fixes side-stream graph capture.
+ if _is_npu:
      shared_output.record_stream(current_stream)
  else:
      shared_alt_output = shared_output
```

- 验证：单台 Ascend A3、12 层 Kimi-K3、TP16/EP16、DSPARK，target/draft 图捕获成功，13 个 probe 请求通过。
- 状态：open，未合入；在其 NPU PR run 中，所有真实 NPU 套件被 precision 选择器跳过（详见第四章）。

## 四、NPU PR 流水线拦截情况

### 4.1 三个上游 PR 的实际 checks

| PR | NPU run | 结论 | Job 统计 | 跳过原因 |
|---|---|---|---|---|
| [#51298](https://github.com/sgl-project/sglang/pull/51298) | [run 44406803384](https://github.com/sgl-project/sglang/actions/runs/44406803384) | success | 22 个：4 success / 18 skipped | 缺 `run-ci-npu-extra` |
| [#50186](https://github.com/sgl-project/sglang/pull/50186) | [run 44504215994](https://github.com/sgl-project/sglang/actions/runs/44504215994) | success | 22 个：4 success / 18 skipped | 缺 `run-ci-npu-extra` |
| [#51900](https://github.com/sgl-project/sglang/pull/51900) | [run 44845789645](https://github.com/sgl-project/sglang/actions/runs/44845789645) | success | 22 个：4 success / 18 skipped | 标签为空，缺 `run-ci` 与 `run-ci-npu-extra` |
| [#53214](https://github.com/sgl-project/sglang/pull/53214)（修复） | [run 45933003123](https://github.com/sgl-project/sglang/actions/runs/45933003123) | success | 仅 `extra-a-test-npu` 执行，`extra-b/c` 全部 skipped | 标签齐全，但 precision 推荐 0 个用例 -> `skip_all` |

> 前三个 run 中成功的 4 个 job 是 `check-changes`、`pr-gate`、`set-image-config`、`Analyze failure report`，没有任何真实 NPU 用例执行。

### 4.2 两种跳过机制

1. **标签门禁**：`pr-gate` 要求同时具备 `run-ci` 和 `run-ci-npu-extra`；三个上游 PR 都没带 `run-ci-npu-extra`。
2. **precision 选择器**：即使标签齐全，`kimi_k3.py` 等模型代码的推荐结果为 0 时，`bucket_recommended_tests.py` 直接 `skip_all`；全量运行只对 3 个 CI 配置文件生效。

### 4.3 如果用例全部运行，能否发现问题？

| 问题 | 套件里有没有对应用例 | 全量运行能否拦截 | 结论 |
|---|---|---|---|
| 问题 1（softcap） | 有：`extra-c-acc-test-16-npu-a3` 中的 DeepSeek-V4-Flash W8A8 8p **DSPARK** 用例 | **能**（startup warmup 就会报 TypeError） | 有拦截能力，但没跑；precision 还可能漏检 |
| 问题 2（107025） | 无：Kimi-K3 32P 只在 nightly 多机；Kimi-K3 单测是 CUDA-only | **不能** | 结构性覆盖缺口 |

关键判断：

- **问题 1 是“没跑”**：PR 套件里有可拦截用例，被标签门禁挡住。
- **问题 2 是“跑不到”**：PR 套件最大单机 16 卡，Kimi-K3 32P 是 4 节点，只有 nightly 才跑。
- **共同问题**：0 个 NPU 用例执行时 workflow 仍显示 success，形成 false green。
