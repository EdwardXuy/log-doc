## 3. 问题 A：A3 DSV4 QLI metadata 2048 vs 1024

### 3.1 现象

Server 已经走到 capture，日志先打印：

```
DSV4 NPU breakable prefill graph: compressor/indexer captured, max 1 request(s) per replay.
```

随后所有 rank 报：

```
RuntimeError: call aclnnQuantLightningIndexerV2 failed, detail:[PID: ...]
Invalid_Argument_Tensor_Shape_Size(EZ0015):
Parameter metadata of QuantLightningIndexerV2 has incorrect shape size 2048.
Reason: The shape size of metadata must be 1024.
```

日志：

- B060 acc：https://github.com/Ascend/sglang/actions/runs/46096421100/job/140828701063
- B060 perf8：https://github.com/Ascend/sglang/actions/runs/46096421100/job/140828701080
- B050 acc：https://github.com/Ascend/sglang/actions/runs/46000693274/job/140511491186

### 3.2 复现配置

A3 DSV4-Flash-w8a8，breakable prefill graph：

- `--tp-size 16 --attn-dp-size 16`（acc）/ `--tp-size 8 --attn-dp-size 8`（perf）
- `--chunked-prefill-size 131072`（acc）/ `8192`（perf）
- `--moe-a2a-backend ascend_ops --moe-ascend-ops-config '{"prefill":"allgather","decode":"low_latency"}'`
- `--cuda-graph-backend-prefill breakable --cuda-graph-bs-prefill 128 512 1024`

排除项：

- 换成 `deepep` 仍复现；
- 桶加 2048 或去掉 2048 都复现；
- B050、B060 都复现；
- 只开 decode graph（SR3）正常。

→ 与 MoE 后端、桶大小、镜像版本无关，是 A3 侧 captured metadata 的分配/ABI 问题。

### 3.3 代码定位

1. captured metadata 分配逻辑：
   https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/hardware_backend/npu/attention/dsv4_prefill_graph.py#L43-L50
   https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/hardware_backend/npu/attention/dsv4_prefill_graph.py#L107-L166

   ```python
   _KERNEL_METADATA_KEYS = (
       "c1a_metadata",
       "c4a_metadata",
       "c128a_metadata",
       "li_quant_metadata",
   )
   _MIN_KERNEL_METADATA_INTS = 1024

   metadata_ints = _MIN_KERNEL_METADATA_INTS
   for tensor in seed.kernel_metadata.values():
       metadata_ints = max(metadata_ints, tensor.numel())
   state.kernel_metadata = {
       key: torch.zeros(metadata_ints, **int32) for key in _KERNEL_METADATA_KEYS
   }
   ```

2. A3 侧 `win/c4a/c128a` metadata 固定按 **2048** int32 分配：
   https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/hardware_backend/npu/attention/ascend_dsv4_backend.py#L2501-L2533

   ```python
   if not is_npu_arch35():
       # BF16 SMLA and its AICPU metadata have a fixed, shared ABI.
       for ratio in (0, *self._dsv41_low_ratios()):
           ...
           if buf is None or buf.numel() != 2048:
               buf = torch.zeros(2048, dtype=torch.int32, device=device)
           ...
           metadata.kernel_metadata[f"{attention_type}_metadata"] = buf
       return
   ```

3. QLI（`QuantLightningIndexerV2`）读取 `li_quant_metadata`：
   https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/hardware_backend/npu/attention/ascend_dsv4_backend.py#L1215-L1232

   ```python
   li_quant_metadata = fm.kernel_metadata["li_quant_metadata"]
   ...
   npu_indexer_ops.quant_lightning_indexer(
       ...,
       metadata=li_quant_metadata,
       ...,
   )
   ```

### 3.4 推断与建议修复

A3 上 `seed.kernel_metadata` 里 `win/c4a/c128a` 的 numel 都是 2048，`allocate()` 取最大值后把
`li_quant_metadata` 也分成了 2048；但 QLI 的 ABI 要求该 metadata 固定为 1024，因此 replay 时被 kernel 拒绝。

建议：

- `li_quant_metadata` 固定分配为 `_MIN_KERNEL_METADATA_INTS`（1024），不参与“所有 key 取最大 numel”的统一分配；
- 或 `allocate()` 按 key 单独决定大小；
- 如果 A3 的 QLI 本来就不该消费 captured `li_quant_metadata`，则 A3 路径应跳过该参数或走 eager。

## 6. 能力边界（需要开发确认）

1. **`MAX_PREFILL_GRAPH_REQS = 1`**：runner 在 prefill batch 请求数 > 1 时回退 eager
   （https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/model_executor/runner/prefill_cuda_graph_runner.py#L1510-L1514）。
   精度用例 `eval_batch_size=128/32`，多数 batch 是多请求，因此只能验证“capture 成功 + 精度不回退”，
   不能验证 replay；replay 由并发=1 的 pure-P perf 用例覆盖。请确认这是预期行为。
2. **A3 是否在支持范围内**：PR #49481 的 Accuracy 小节只贴了 A5 结果，并注明
   “End-to-end logprob parity and Ascend 950 capture/replay are still being validated”。
3. **DSPARK + draft model**：开发脚本是纯 P 无投机；A3/A5 用例带 DSPARK，BCG replay 正确性未验证。
